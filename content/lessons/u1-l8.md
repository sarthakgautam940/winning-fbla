Every data science project, from a class project to a hospital's readmission model, moves through the same broad stages: define the question, get the data, clean it, explore it, model it, evaluate the result, and put it to use. The official objective asks you to "describe the stages of the data science process," and test writers check it three ways: putting stages in order, deciding which stage an activity belongs to, and naming the phases of the well-known process models. This lesson covers the general lifecycle, the named models (OSEMN, CRISP-DM, and IBM's methodology), exploratory data analysis, and the habits that make work trustworthy.

## The lifecycle from question to deployment

Strip away the different names and almost every process model shares these stages:

1. **Define the problem.** What decision needs to be made, and what would a useful answer look like? This sets which data you need and how success will be measured.
2. **Collect the data** from the sources that can answer the question.
3. **Clean and prepare** the data: the wrangling from lesson 1.7.
4. **Explore** the data to understand its patterns and problems.
5. **Model**: build and train models or run analyses.
6. **Evaluate**: check the results against the original goal.
7. **Deploy and communicate**: put the model into use or present the findings to the people who will act on them.
8. **Monitor and maintain**: watch how the model performs over time and update it when the world changes.

```figure
type: flow
caption: The data science lifecycle is a loop. Monitoring and new questions lead back to the start.
cycle: true
steps: [Define the problem, Collect data, Clean and prepare, Explore, Model, Evaluate, Deploy and communicate, Monitor]
```

Two facts about this sequence appear on tests constantly. First, the process **starts with the question**, not with the data. Collecting data before you know what you are trying to answer risks gathering the wrong data and measuring the wrong thing. Second, the process is **iterative**: later stages often send you back to earlier ones. Exploration may reveal that a key variable is missing, which sends you back to collection; a disappointing evaluation sends you back to preparation or modeling.

Deployment is not the end either. A model trained on last year's behavior can slowly get worse as customers, prices, or seasons change, a problem called **model drift**. Monitoring catches it so the model can be retrained.

## OSEMN

One of the best-known short frameworks is **OSEMN**, pronounced "awesome," from a 2010 post by data scientists Hilary Mason and Chris Wiggins. It names five steps:

| Step | What happens |
|---|---|
| **O**btain | Gather data from sources: databases, files, APIs, scraping |
| **S**crub | Clean the data: fix errors, handle missing values, convert formats |
| **E**xplore | Examine the data with statistics and charts to find patterns |
| **M**odel | Build models to predict or explain |
| i**N**terpret | Explain what the results mean and communicate them |

OSEMN is easy to remember but leaves two stages implicit: it does not begin with an explicit problem-definition step, and it does not include deployment or monitoring.

::check{id="process-models-01"}

## CRISP-DM's six phases [Competitive]

**CRISP-DM** (Cross-Industry Standard Process for Data Mining) was developed by an industry consortium (DaimlerChrysler, SPSS, NCR, and the Dutch insurer OHRA), with work starting in the late 1990s and version 1.0 released in 2000. It has six phases, in this order:

```figure
type: flow
caption: CRISP-DM's six phases. Projects move back and forth between phases, and the outer loop shows the cycle repeating.
cycle: true
steps: [Business Understanding, Data Understanding, Data Preparation, Modeling, Evaluation, Deployment]
```

1. **Business Understanding**: define the objectives and requirements from the organization's point of view and turn them into a data problem.
2. **Data Understanding**: collect initial data, describe it, explore it, and check its quality.
3. **Data Preparation**: select, clean, construct, integrate, and format the final dataset.
4. **Modeling**: select modeling techniques, build models, and tune them.
5. **Evaluation**: check whether the model meets the business objectives, and review the process before deciding to deploy.
6. **Deployment**: put the results into use, with plans for monitoring and maintenance.

The order is not rigid. The official guide stresses that projects move back and forth between phases as needed: understanding the data often changes the business question, and modeling often sends you back to preparation. Practitioners commonly report that data preparation consumes more time than any other phase.

:::trap
**Common trap.** Modeling and evaluation are different phases. Evaluation asks whether the model meets the **business** objective set in Business Understanding, not only whether its accuracy is high. A model with excellent test accuracy that does not help anyone decide anything fails evaluation.
:::

::check{id="process-models-02"}

## IBM's data science methodology [Competitive]

IBM's Data Science Professional Certificate, one of the official references for this event, teaches a methodology described by John Rollins of IBM in 2015. It has **10 iterative stages**:

| Stage | Question it answers |
|---|---|
| 1. Business understanding | What problem are you trying to solve? |
| 2. Analytic approach | How can data answer the question: descriptive, predictive, classification? |
| 3. Data requirements | What data, in what formats, is needed? |
| 4. Data collection | Where does it come from, and how is it gathered? |
| 5. Data understanding | Does the collected data represent the problem? |
| 6. Data preparation | How must the data be cleaned and organized? |
| 7. Modeling | Which model answers the question? |
| 8. Evaluation | Does the model really answer the question? |
| 9. Deployment | How is the model put into use? |
| 10. Feedback | What do users' results say, and how should the model be refined? |

Compared with CRISP-DM, IBM's version splits the early work into more stages (an explicit analytic-approach step and separate requirements, collection, and understanding steps) and ends with feedback, closing the loop back to refinement.

One older model also appears in references. **KDD**, the Knowledge Discovery in Databases process described by Fayyad, Piatetsky-Shapiro, and Smyth in 1996, runs selection, preprocessing, transformation, data mining, and interpretation or evaluation. In KDD, **data mining is one step** inside the larger discovery process, not the whole of it.

::check{id="process-models-03"}

## Exploratory data analysis

**Exploratory data analysis (EDA)** is the initial investigation of a dataset, mainly with summary statistics and visualizations, to understand its structure, spot patterns, outliers, and errors, and form questions before formal modeling. The approach is closely associated with the statistician John Tukey, whose 1977 book *Exploratory Data Analysis* championed looking at data before testing ideas about it.

A typical EDA pass looks at:

- **Each variable alone**: its distribution (histograms, boxplots), center and spread, and its minimum and maximum, which often expose errors such as an age of 340.
- **Missing values**: how many, and in which columns.
- **Relationships**: scatterplots and correlations between pairs of variables, and comparisons between groups.
- **Data types and categories**: whether numbers are stored as numbers, and which categories appear and how often.

In pandas, `describe()` gives a quick numeric summary:

```python run
import pandas as pd

df = pd.DataFrame({
    "grade": [10, 11, 12, 10, 11, 12, 9, 11],
    "gpa": [3.6, 2.9, 3.9, 3.2, 3.8, 2.5, 3.4, None],
})
print(df["gpa"].describe().round(2))
print(df["gpa"].isna().sum())
```

```output
count    7.00
mean     3.33
std      0.50
min      2.50
25%      3.05
50%      3.40
75%      3.70
max      3.90
Name: gpa, dtype: float64
1
```

The count of 7 out of 8 rows and the final 1 both reveal a missing GPA. The 50% row is the median, and `std` is the sample standard deviation.

EDA is different from **confirmatory analysis**. EDA explores openly and generates hypotheses; confirmatory analysis, such as a formal statistical test or a carefully evaluated model, tests a specific hypothesis. EDA happens after data is collected and cleaned enough to read, and before modeling, though you return to it whenever something surprising appears.

## Reproducibility, documentation, and communicating results

Work is **reproducible** when someone else, or you a month later, can rerun it from the original data and get the same results. Reproducibility is what makes a finding trustworthy. The habits that create it:

- **Keep the raw data unchanged** and do every cleaning step in code, never by hand-editing cells, so each step can be traced and repeated.
- **Use notebooks**, such as **Jupyter**, which combine code, its output, and written explanation in one document. Jupyter grew out of the IPython project in 2014, and its name comes from the three languages it first supported: Julia, Python, and R.
- **Use version control**, such as **Git**, to record every change to code and files so earlier versions can be restored and collaborators' work combined.
- **Set random seeds**, so random steps such as data splits and model initializations come out the same on every run.
- **Record the environment**: which packages and versions the code used.
- **Document**: a README explaining the project, comments in code, and a data dictionary for the fields.

The last stage of a project is often **communication**, and a correct analysis that nobody understands changes nothing. Good data communication knows its audience, leads with the main finding and what to do about it, uses one clear chart rather than ten, states uncertainty and limitations honestly, and saves technical detail for those who ask. This is sometimes called **data storytelling**: context, finding, implication, recommendation.

:::tip
**Test tip.** If a question asks which practice makes an analysis reproducible, look for code, version control, seeds, or documentation. Manual edits, undocumented steps, and overwritten raw files are the wrong answers.
:::

:::takeaways
- Lifecycle: define the problem, collect, clean and prepare, explore, model, evaluate, deploy and communicate, monitor. It starts with the question and is iterative.
- Monitoring after deployment catches model drift, when changing conditions make a model worse over time.
- OSEMN (Mason and Wiggins, 2010): obtain, scrub, explore, model, interpret.
- CRISP-DM (consortium, 1.0 in 2000): Business Understanding, Data Understanding, Data Preparation, Modeling, Evaluation, Deployment. The order is flexible, and preparation usually takes the most time.
- Evaluation checks the business objective, not just a metric.
- IBM (Rollins, 2015), 10 stages: business understanding, analytic approach, data requirements, data collection, data understanding, data preparation, modeling, evaluation, deployment, feedback.
- KDD (Fayyad and colleagues, 1996): data mining is one step within knowledge discovery.
- EDA (associated with Tukey, 1977) explores data with summaries and charts before modeling; confirmatory analysis tests hypotheses.
- Reproducibility: untouched raw data, code instead of manual edits, notebooks, Git, random seeds, recorded environments, documentation.
:::
