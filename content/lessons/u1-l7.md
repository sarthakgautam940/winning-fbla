Raw data almost never arrives ready to analyze. Dates come in three formats, prices are stored as text with dollar signs, one state is spelled four ways, and a model that needs numbers is handed words. Turning that mess into clean, consistent, model-ready data is the subject of this lesson. The official objective asks you to "describe the importance of data wrangling and transformation," and the test adds quick calculations: scaling a value, counting the columns one-hot encoding creates, and choosing the right transformation for a situation.

## What wrangling is and why it takes so much of a project

**Data wrangling** (also called data munging) is the process of turning raw data into a clean, structured, usable form for analysis. It covers discovering what is wrong with the data, restructuring it, cleaning it, combining sources, and checking the result.

**Data transformation** is the part of wrangling that converts data from one format, structure, or scale to another: changing units, reshaping a table, scaling numbers, or encoding categories as numbers.

Picture combining three files for a sales analysis: a CSV with dates written as 03/04/26, a JSON product feed with prices stored as text like "$1,200", and a spreadsheet where missing values are typed as "N/A", "none", or left blank. None of the three can be analyzed together until they are wrangled into one consistent table.

Wrangling matters because every analysis and every model is only as good as the data fed into it. Errors, inconsistent formats, and missing values that slip through produce wrong averages, misleading charts, and models that learn the wrong patterns. That is also why wrangling and cleaning often take up more of a project's time than any other step.

:::key
**Key idea.** Wrangling turns raw data into analysis-ready data. It is not busywork: a model cannot be better than the data it learns from.
:::

## Tidy data: one variable per column, one observation per row

A widely used standard for how a clean table should look is **tidy data**, defined by statistician Hadley Wickham in a 2014 paper. Its three rules:

1. Each variable forms a column.
2. Each observation forms a row.
3. Each type of observational unit forms a table.

The book *R for Data Science* states the third rule as "each value is a cell". Know both versions.

Here is a common untidy layout. The test names are values of a variable, but they are spread across the column headers:

| student | test1 | test2 | test3 |
|---|---|---|---|
| Ava | 88 | 92 | 85 |
| Ben | 75 | 81 | 79 |

The tidy version has one column per variable (student, test, score) and one row per observation (one student's score on one test):

| student | test | score |
|---|---|---|
| Ava | test1 | 88 |
| Ava | test2 | 92 |
| Ava | test3 | 85 |
| Ben | test1 | 75 |
| Ben | test2 | 81 |
| Ben | test3 | 79 |

The first layout is called **wide** format (one row per subject, many measurement columns) and the second is **long** format (one row per measurement). Neither is wrong for every purpose, but analysis tools work most easily with tidy, long data. In pandas, `melt` turns wide into long and `pivot` turns long into wide; in R, `pivot_longer` and `pivot_wider` do the same.

Other untidy patterns to recognize: two variables stored in one column (a column of codes such as "F_16" combining sex and age), and one variable split across several tables.

## Parsing and type conversion

**Parsing** means reading raw text and turning it into structured values: splitting "Ava Lopez" into a first and last name, pulling the year out of "2026-03-14", or reading a date string as an actual date.

Dates deserve special care. The string 03/04/2026 is March 4 in the United States but April 3 in much of the world, which writes the day first. When sources from different places are combined, each must be parsed with its own format.

**Type conversion** (or casting) changes a value's data type. Numbers often arrive stored as text: "1,200" has a comma, "$35.00" has a dollar sign, and placeholders such as "N/A", "?", or "none" stand for missing values. Until they are converted, a program cannot add or average them. In pandas:

```python run
import pandas as pd

prices = pd.Series(["$12.50", "$8", "N/A", "$1,200"])
clean = pd.to_numeric(prices.str.replace("[$,]", "", regex=True), errors="coerce")
print(clean.tolist())
```

```output
[12.5, 8.0, nan, 1200.0]
```

The code strips dollar signs and commas, then converts to numbers; `errors="coerce"` turns anything unconvertible, such as "N/A", into `nan`, pandas' marker for a missing value.

Wrangling also **standardizes** values that mean the same thing: "NY", "New York", and "new york" become one label, and weights recorded partly in pounds and partly in kilograms are converted to one unit. Without this, a count by state would treat one state as three.

:::trap
**Common trap.** A column that looks numeric on screen may be stored as text. If an average or a sort behaves strangely ("1,200" sorting before "35"), suspect a type problem before anything else.
:::

## Scaling: min-max normalization and z-score standardization

Features often live on wildly different scales. Income might run from 20,000 to 200,000 while age runs from 18 to 90. Many algorithms are thrown off by that difference:

- Methods based on **distance**, such as k-nearest neighbors and k-means clustering, would let income dominate, because a difference of 1,000 dollars dwarfs a difference of 10 years.
- Models trained with **gradient descent**, such as linear and logistic regression and neural networks, train slowly or unstably when features have very different ranges.

Two standard fixes put features on comparable scales.

**Min-max normalization** rescales values to the range 0 to 1:

$$
x' = \frac{x - \min}{\max - \min}
$$

The minimum becomes 0, the maximum becomes 1, and everything else falls in between.

**Z-score standardization** rescales values to have mean 0 and standard deviation 1:

$$
z = \frac{x - \bar{x}}{s}
$$

Each value becomes its distance from the mean in standard deviations, exactly the z-score you will meet again in lesson 2.5.

::::example[Scaling one value both ways]
Ages in a dataset range from 18 to 90, with mean 45 and standard deviation 18. Scale the age 54 both ways.

:::step
Min-max: subtract the minimum and divide by the range. (54 - 18) / (90 - 18) = 36 / 72 = 0.5.
:::

:::step
Z-score: subtract the mean and divide by the standard deviation. (54 - 45) / 18 = 9 / 18 = 0.5.
:::

:::answer
Both give 0.5 here, by coincidence. Min-max says 54 is halfway between the youngest and oldest; the z-score says 54 is half a standard deviation above the mean.
:::
::::

How to choose:

- **Min-max** gives a fixed 0-to-1 range, which suits pixel values or inputs that must be bounded. But it is very sensitive to outliers: a single extreme value becomes the maximum and squashes everything else into a narrow band near 0.
- **Standardization** has no fixed range but is less distorted by a single outlier, and it is the usual default for many machine learning algorithms. For data full of outliers, a variant that uses the median and interquartile range is less sensitive still.
- **Tree-based models** such as decision trees and random forests do not need scaling, because each split compares one feature to a threshold, and rescaling does not change which side of the threshold a value falls on.

One rule matters a great deal: compute the minimum, maximum, mean, and standard deviation from the **training data only**, then apply those same numbers to the validation and test data. Computing them from all the data lets information about the test set leak into training, a problem called data leakage that you will study in Unit 5.

:::trap
**Common trap.** "Normalization" has two meanings. Here it means scaling values, usually to 0 to 1. In databases (Unit 4) it means organizing tables to reduce redundancy. Read the context.
:::

## Encoding categories: one-hot and label encoding

Most models only accept numbers, so categorical features must be encoded.

**Label encoding** (or ordinal encoding) replaces each category with an integer: small = 0, medium = 1, large = 2. That is the right choice for **ordinal** data, because the numbers keep the real order. It is the wrong choice for **nominal** data: coding red = 0, green = 1, blue = 2 tells the model that blue is "bigger" than green and that green sits exactly halfway between red and blue, which is meaningless.

**One-hot encoding** creates one new 0-or-1 column per category. Each row has a 1 in the column for its category and 0s everywhere else, so no false order is introduced:

```python run
import pandas as pd

df = pd.DataFrame({"color": ["red", "green", "blue", "green"]})
print(pd.get_dummies(df, columns=["color"], dtype=int))
```

```output
   color_blue  color_green  color_red
0           0            0          1
1           0            1          0
2           1            0          0
3           0            1          0
```

A feature with **k categories** becomes **k columns**. Often one column is dropped (`drop_first=True` in pandas), leaving **k - 1**: a row of all zeros then means the dropped category. Dropping one avoids the **dummy variable trap**: in a linear regression with an intercept, keeping all k columns makes them perfectly redundant, since any one column can be computed from the others.

One-hot encoding has a weakness: a feature with thousands of categories, such as product IDs or ZIP codes, explodes into thousands of mostly-zero columns. Common fixes include grouping rare categories into "Other" or replacing each category with a single number such as how often it appears.

## Binning, log transforms, and new features [Competitive]

**Binning** (or discretization) turns a continuous variable into ranges: ages become 0 to 17, 18 to 34, 35 to 54, and 55 and up. There are two main ways to draw the bins:

- **Equal-width** bins each cover the same range of values. Ages 20 to 80 in 4 equal-width bins gives bins 15 years wide.
- **Equal-frequency** (quantile) bins each hold the same number of observations: 1,000 households in 4 bins of 250 each.

A **log transform** replaces each value with its logarithm. It is the standard fix for **right-skewed** positive data such as incomes, prices, and city populations, where a few huge values stretch the scale. With base-10 logs, 1,000 becomes 3, 100,000 becomes 5, and 10,000,000 becomes 7: huge gaps shrink to steps of 2, and the distribution becomes far more symmetric.

**Feature engineering** is creating new input variables from existing data so a model can learn better. It is often where domain knowledge pays off most. Common moves:

- **Ratios and differences**: debt-to-income ratio, price per square foot.
- **Date parts**: day of week, month, hour, or a weekend flag from a timestamp.
- **Aggregates**: number of purchases in the last 30 days.
- **Combinations**: price times quantity gives revenue.

Two related terms: **feature selection** keeps the most useful of the existing features and drops the rest, while **feature extraction** builds a smaller set of new features from many old ones, as principal component analysis does (Unit 3).

::::example[Engineering features for a shop]
An online shop has each order's timestamp, the customer's ID, and the order total. It wants to predict which customers will buy again. Suggest three engineered features.

:::step
From the timestamp: whether the order was on a weekend, and the hour of day.
:::

:::step
Aggregated by customer: number of orders in the last 90 days, and days since the last order.
:::

:::step
A ratio: average order total, which is total spending divided by number of orders.
:::

:::answer
Weekend flag and hour, recent order count and days since last order, and average order value are all strong candidates. None existed as columns until they were engineered.
:::
::::

:::takeaways
- Data wrangling turns raw data into clean, structured, usable data; data transformation converts format, structure, or scale. Messy inputs produce wrong results.
- Tidy data (Wickham, 2014): each variable a column, each observation a row, each type of observational unit a table ("each value a cell" in R for Data Science). Wide tables can be melted into long ones.
- Parse dates with each source's own format (03/04 may be March 4 or April 3). Convert text numbers such as "$1,200" to numeric types, and standardize labels and units.
- Min-max normalization (x - min) / (max - min) gives 0 to 1 and is outlier-sensitive. Standardization (x - mean) / SD gives mean 0 and SD 1.
- Scale features for distance-based methods and gradient descent; trees do not need scaling. Fit scaling statistics on training data only.
- Label encoding suits ordinal data; one-hot encoding suits nominal data. k categories make k one-hot columns, or k - 1 with one dropped to avoid the dummy variable trap.
- Equal-width bins share a range size; equal-frequency bins share a count. Log transforms tame right skew.
- Feature engineering builds new inputs: ratios, date parts, aggregates, combinations. Selection keeps features; extraction builds new ones.
:::
