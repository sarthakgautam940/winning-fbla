title: Rule-based reasoning and expert systems
---

Rules are the most direct way to put expert knowledge into a program, and an inference engine can use them in two directions: forward from the facts, or backward from a goal. This lesson traces both, takes apart the classic expert system, and ends with how today's AI combines rules and logic with neural networks. Expect "forward or backward?" scenarios, short traces of a rule base, and questions on the parts of an expert system.

## Rules and facts

A **rule-based system** keeps two kinds of knowledge:

- **Facts** describe the current case: what is known right now. They are kept in a **working memory**.
- **Rules** are IF-THEN statements (lesson 7.2) that say what follows from what. They are kept in a **knowledge base**, sometimes called production memory.

An **inference engine** connects them: it repeatedly matches rules against facts and applies the ones that fit. Here is a small rule base for identifying animals, which the next two sections use:

```text
R1: IF the animal has feathers THEN it is a bird
R2: IF the animal has fur THEN it is a mammal
R3: IF it is a bird AND it swims AND it cannot fly THEN it is a penguin
R4: IF it is a mammal AND it swims AND it has whiskers THEN it is an otter
```

Suppose the working memory holds three facts about an animal: it has feathers, it swims, and it cannot fly. What is it? There are two ways to find out.

::check{id="chaining-13"}

## Forward chaining: data-driven

**Forward chaining** is data-driven reasoning: it starts from the known facts and repeatedly applies every rule whose conditions are all satisfied, adding the rule's conclusion to the facts, until no rule can add anything new or a goal is reached.

::::example[Trace forward chaining]
Facts: has feathers, swims, cannot fly. Run forward chaining on rules R1 to R4.

:::step
Cycle 1: R1's condition, has feathers, is true, so R1 fires and adds "it is a bird." R2 and R4 need fur or mammal, and R3 needs "bird," which is not yet known when the cycle begins.
:::

:::step
Cycle 2: R3's conditions are now all true (bird, swims, cannot fly), so R3 fires and adds "it is a penguin."
:::

:::step
Cycle 3: No rule adds anything new, so forward chaining stops.
:::

:::answer
Forward chaining derived two new facts: the animal is a bird, and it is a penguin. It never asked a question; it simply pushed the data as far as the rules allowed.
:::
::::

Forward chaining suits problems where data arrives and you want to know everything that follows: monitoring systems that raise alarms as sensor readings come in, and configuration tasks that build up a design step by step. The classic example is R1, also known as XCON, which configured Digital Equipment Corporation's VAX computer orders. It ran in OPS4, a production system language whose recognize-act cycle repeatedly finds every rule that matches the current data and fires one of them, and by 1980 it had 772 rules. The downside of forward chaining is that it can derive many facts that have nothing to do with the question you care about.

## Backward chaining: goal-driven

**Backward chaining** is goal-driven reasoning: it starts from a goal, a hypothesis to prove, finds rules that would conclude it, and tries to prove those rules' conditions as subgoals, working backward until it reaches known facts or must ask the user.

::::example[Trace backward chaining]
Goal: is the animal a penguin? Use rules R1 to R4, and ask the user about any fact that no rule concludes.

:::step
Only R3 concludes "penguin," so its three conditions become subgoals: bird, swims, and cannot fly.
:::

:::step
"Bird" is concluded by R1, so its condition, has feathers, becomes a new subgoal. No rule concludes "has feathers," so the system asks the user, who says yes. That proves "bird."
:::

:::step
No rules conclude "swims" or "cannot fly," so the system asks about each; the user says yes to both.
:::

:::answer
Every condition of R3 is proven, so the goal is confirmed: the animal is a penguin. The system asked only questions relevant to the goal and never considered R2 or R4.
:::
::::

Backward chaining suits diagnosis and question answering, where you have a specific hypothesis to check and want to ask only relevant questions. MYCIN, the Stanford expert system that advised doctors on antibiotic treatment, used a goal-oriented control structure of exactly this kind, and logic programming languages such as Prolog answer queries by working backward from the query.

| | Forward chaining | Backward chaining |
|---|---|---|
| Starts from | Known facts (data) | A goal or hypothesis |
| Works | From conditions to conclusions | From conclusions back to conditions |
| Best for | Monitoring, configuration, finding all consequences | Diagnosis, confirming a hypothesis, answering a specific question |
| Classic example | R1/XCON configuring computer orders | MYCIN diagnosing infections; Prolog queries |
| Weakness | Can derive many irrelevant facts | Inefficient when there are many possible goals |

:::tip
**Test tip.** "Data-driven," "starts with the facts," or "what follows from these readings?" means forward chaining. "Goal-driven," "starts with a hypothesis," or "is it true that...?" means backward chaining.
:::

## Expert systems and their parts

An **expert system** is a program that captures the knowledge of human experts in a narrow domain and uses it to give advice or solve problems at an expert level. Its parts:

| Part | Job |
|---|---|
| **Knowledge base** | The domain knowledge: facts and IF-THEN rules gathered from experts |
| **Inference engine** | Applies the rules to the facts, by forward or backward chaining, to reach conclusions |
| **Working memory** | The facts about the current case |
| **User interface** | Asks the user questions and presents advice |
| **Explanation facility** | Shows how a conclusion was reached and why a question is being asked |
| **Knowledge acquisition component** | Tools for adding and updating rules |

The people who interview experts and turn their know-how into rules are **knowledge engineers**. The original MYCIN had about 200 rules, each with a premise, an action, and sometimes an else clause, and it attached a numerical degree of certainty to its conclusions; it was never put into routine clinical use. R1/XCON, by contrast, was in regular use at Digital Equipment Corporation.

Expert systems are consistent, can explain every conclusion, and spread scarce expertise. Their weaknesses explain why the second AI winter followed their boom (lesson 6.1): extracting rules from experts is slow and difficult, a problem called the **knowledge acquisition bottleneck**; the systems are brittle outside their narrow domain; large rule bases are hard to maintain; and they do not learn from data on their own.

## Symbolic and connectionist AI together [Competitive]

Lesson 6.1 introduced AI's two traditions. **Symbolic** AI, such as rules, logic, and knowledge graphs, is explicit, explainable, and precise, but it must be built by hand and it is brittle. **Connectionist** AI, neural networks, learns from raw data such as images and text, but it is hard to explain and can make confident mistakes. Their strengths are complementary, so many modern systems combine them, an approach called **neuro-symbolic AI**:

- **Perception plus reasoning.** A neural network recognizes objects in a camera image, and symbolic rules reason about them: a vehicle's network detects a stop sign, and a rule says to stop.
- **Learning plus search.** DeepMind's AlphaGo combined deep neural networks, which evaluated board positions and suggested moves, with tree search, which looked ahead through possible sequences of play (lesson 5.3).
- **Knowledge graphs with machine learning.** Language models can extract entities and relationships from text to build knowledge graphs (lesson 6.2), and in the other direction, facts retrieved from a knowledge graph can ground an LLM's answers and reduce hallucination, as in retrieval-augmented generation (lesson 6.5).

Explicit knowledge still matters even in the age of deep learning:

- **Hard constraints.** Laws and safety rules, such as "never use a protected attribute in a lending decision," should be guaranteed by explicit rules rather than hoped for from learned patterns.
- **Explanation and audit.** A rule that fired can be shown to a regulator or a customer.
- **Little data.** Expert rules let a system work where there is too little data to learn from.
- **Easy correction.** A wrong fact in a knowledge base can be fixed directly, while a neural network must be retrained.

::check{id="kr-ml-01"}

:::takeaways
- A rule-based system keeps facts in working memory and IF-THEN rules in a knowledge base; an inference engine matches rules to facts.
- Forward chaining is data-driven: start from facts, fire every rule whose conditions hold, and add conclusions until nothing new appears. It suits monitoring and configuration (R1/XCON, a production system with a recognize-act cycle and 772 rules by 1980).
- Backward chaining is goal-driven: start from a hypothesis, find rules that conclude it, and prove their conditions as subgoals, asking only relevant questions. It suits diagnosis (MYCIN's goal-oriented control) and Prolog queries.
- An expert system has a knowledge base, an inference engine, working memory, a user interface, an explanation facility, and knowledge acquisition tools; knowledge engineers build it.
- Expert systems are consistent and explainable but suffer from the knowledge acquisition bottleneck, brittleness, maintenance burdens, and no learning.
- Neuro-symbolic AI combines neural perception and learning with symbolic rules, logic, and search (AlphaGo: neural networks plus tree search). Knowledge graphs and LLMs help each other.
- Explicit knowledge still matters for hard constraints, explanation, low-data settings, and quick correction.
:::
