title: Structured, semi-structured, and unstructured data
---

Before anyone can analyze data, they have to know what shape it is in. A table of sales, a folder of customer emails, and a stream of photos from a delivery drone all count as data, but each one is stored, searched, and analyzed differently. The test asks you to classify examples by structure, recognize file formats on sight, know where each kind of data is stored, and define metadata. This lesson covers all four.

## Structured data: rows, columns, and a schema

**Structured data** is organized into a fixed format of rows and columns, where every column has a defined name and data type. That definition is called a **schema**: the blueprint that says which fields exist, what type each one holds (integer, text, date), and which rules they follow.

Here are a few rows from the course's sample school database:

| student_id | name | grade | gpa |
|---|---|---|---|
| 1 | Ava | 10 | 3.6 |
| 2 | Ben | 11 | 2.9 |
| 3 | Chloe | 12 | 3.9 |

Each row is one **record** (one student). Each column is one **field** (one variable), and every value in a column has the same type. Because the structure is known in advance, a computer can search, filter, sort, and total structured data instantly. Asking "What is the average GPA of grade 11 students?" takes one line of SQL.

Structured data lives in relational databases, spreadsheets, and CSV files. Bank transactions, inventory tables, student records, and sensor readings logged as timestamped numbers are all typical examples.

:::key
**Key idea.** Structured data fits a predefined schema of rows and columns. That predictability is what makes it easy to query and analyze.
:::

## Unstructured data: text, images, audio, video

**Unstructured data** has no predefined data model or schema. Free text (emails, product reviews, social media posts, essays, PDFs), images, audio recordings, and video are all unstructured. It is a large and fast-growing share of the data organizations collect.

Unstructured does not mean the data has no organization at all. A photo is a grid of pixels, and an email is a sequence of words. What is missing is a schema that labels the *meaning* of the content in fields you can query. Nothing in a photo's pixels says "this is a dog" in a column you can filter on.

That is why unstructured data is harder to analyze. You first have to extract features from it, usually with artificial intelligence:

- **Text** needs natural language processing (NLP) to find topics, names, or sentiment.
- **Images and video** need computer vision to detect objects or faces.
- **Audio** needs speech recognition to turn sound into words.

:::trap
**Common trap.** Storing something in a database does not make it structured. A table with a column of free-text customer comments is structured, but the comment text inside that column is unstructured: you still need NLP to learn what customers are saying.
:::

## Semi-structured data: JSON, XML, logs [Competitive]

Between the two sits **semi-structured data**: data that does not fit a fixed table, but carries tags, keys, or markers that label its parts. Each record describes itself, so records can have different fields, and fields can contain lists or other records inside them (**nesting**).

The most common semi-structured formats are **JSON** (JavaScript Object Notation) and **XML** (eXtensible Markup Language). Here is one student written both ways:

```json
{
  "student_id": 1,
  "name": "Ava",
  "grade": 10,
  "clubs": ["Robotics", "Chess"]
}
```

```xml
<student id="1">
  <name>Ava</name>
  <grade>10</grade>
  <clubs>
    <club>Robotics</club>
    <club>Chess</club>
  </clubs>
</student>
```

JSON labels each value with a key (`"name": "Ava"`); XML wraps each value in opening and closing tags (`<name>Ava</name>`). Notice the list of clubs: a single table cell cannot hold a list cleanly, but both formats nest it naturally. Web APIs usually send JSON. Other semi-structured examples include HTML pages, server log files with labeled fields, and the documents stored in NoSQL databases.

:::tip
**Test tip.** Ask one question: is there a fixed schema? Yes means structured. Labels but no fixed schema (keys, tags) means semi-structured. No schema and no labels on the content means unstructured.
:::

::check{id="data-structure-03"}

## File formats side by side

You should recognize the common formats on sight and know what each is good for.

| Format | Structure | Strengths | Limits |
|---|---|---|---|
| CSV (comma-separated values) | Structured | Plain text, opens anywhere, simple | No data types, no nesting |
| TSV (tab-separated values) | Structured | Same as CSV; tabs avoid comma problems | Same as CSV |
| Excel workbook (.xlsx) | Structured | Multiple sheets, formulas, formatting | Not built for very large data |
| JSON | Semi-structured | Nesting, key-value pairs, the language of web APIs | Harder to load straight into a table |
| XML | Semi-structured | Tags and attributes, strict validation | Wordy, larger files |
| Parquet | Structured | Columnar, compressed, stores its schema; fast for big analytics | Binary, not human-readable |
| Text, PDF | Unstructured | Natural for documents | Needs NLP to analyze |
| Images, audio, video (PNG, JPEG, MP3, MP4) | Unstructured | Rich information | Large; needs AI to analyze |

A **CSV** file is plain text with one record per line and commas between fields. The first line is usually a header row of column names:

```csv
student_id,name,grade,gpa
1,Ava,10,3.6
2,Ben,11,2.9
```

Because a CSV file stores only text, it carries no data types. A program reading it must guess that `3.6` is a number, and a ZIP code such as `02134` can lose its leading zero if it is read as a number. Values that contain commas must be wrapped in quotes.

**Parquet** works differently. CSV stores data row by row; Parquet is a **columnar** format that stores all the values of each column together, compressed. When an analysis needs only 3 columns of a 200-column table with a billion rows, a columnar file lets the computer read just those 3 columns. Similar values sitting side by side also compress well. That is why Parquet is common in big data systems.

## Where each kind of data lives [Competitive]

Organizations store data in a few standard places:

- A **relational database** stores structured data in related tables and enforces the schema every time data is written.
- A **data warehouse** is a central store of cleaned, structured data combined from many sources, organized for reporting and analysis. A **data mart** is a smaller slice of a warehouse focused on one department, such as sales.
- A **data lake** stores raw data of any kind, structured, semi-structured, or unstructured, in its original format. It is cheap and flexible, but without good organization it can turn into a "data swamp" that nobody can find anything in.
- A **data lakehouse** combines a lake's flexible storage with warehouse-style organization and management.

The warehouse and the lake reflect two opposite strategies. A warehouse uses **schema-on-write**: data is cleaned and fitted to a schema before it is stored, so it is ready to query. A lake uses **schema-on-read**: data is stored as it arrives, and a structure is applied only when someone reads it for an analysis. Schema-on-write is faster and more reliable to query; schema-on-read is more flexible and keeps data you have not yet found a use for.

:::trap
**Common trap.** Students reverse the two. Warehouse means clean and structured first (schema-on-write). Lake means store everything raw and decide later (schema-on-read).
:::

## Metadata and data dictionaries

**Metadata** is data about data: information that describes a dataset or file rather than being its main content. A photo's pixels are the data; the camera model, date taken, and GPS location stored inside the file are metadata (in photos this embedded metadata is called **EXIF** data). For a table, the column names, data types, number of rows, source, and last-updated date are metadata.

Metadata is often sorted into three types:

| Type | What it describes | Examples |
|---|---|---|
| Descriptive | What the data is, to help find it | Title, author, keywords, summary |
| Structural | How the data is organized | Column names and types, table relationships, page order |
| Administrative | How the data is managed | Creation date, owner, access permissions, file format, rights |

A **data dictionary** is a document of metadata for a dataset. For each field it lists the name, data type, meaning, units, and allowed values:

| Field | Type | Meaning | Allowed values |
|---|---|---|---|
| grade | integer | Student's grade level | 9 to 12 |
| gpa | decimal | Unweighted grade point average | 0.0 to 4.0, or blank if not yet recorded |

Metadata matters because data without it is hard to find, easy to misread, and impossible to trust. Knowing when a dataset was last updated tells you whether it is current; knowing its source tells you whether it is credible. Metadata can also be sensitive: a photo's GPS coordinates can reveal where someone lives.

:::takeaways
- Structured data fits a predefined schema of rows and columns (databases, spreadsheets, CSV) and is easy to query.
- Unstructured data has no schema (text, images, audio, video) and needs NLP, computer vision, or speech recognition to analyze.
- Semi-structured data labels its parts with keys or tags but has no fixed schema (JSON, XML, HTML, logs); it can nest lists and records.
- CSV is plain text with commas and no data types. Parquet is columnar and compressed, fast for reading a few columns of huge data.
- Warehouse: cleaned, structured, schema-on-write. Lake: raw data of any kind, schema-on-read. Mart: a department's slice of a warehouse.
- Metadata is data about data: descriptive (find it), structural (how it is organized), administrative (how it is managed).
- A data dictionary lists each field's name, type, meaning, units, and allowed values.
:::
