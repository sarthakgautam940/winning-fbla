A spreadsheet, a song, a selfie, and a text message all end up as long strings of 0s and 1s. Knowing how they are encoded lets you answer a whole family of quick test questions: how many values some number of bits can hold, how big a file is, why a "1 TB" drive shows less space, what the ASCII code for a letter is, and what color #FF8000 is. The champion-level questions go further, into overflow, negative numbers, and why computers sometimes get decimal arithmetic slightly wrong. This lesson covers all of it.

## Bits, bytes, and how many values n bits can hold

A **bit** (binary digit) is a single 0 or 1, the smallest unit of data. Bits are grouped into larger units:

| Unit | Size | Values it can hold |
|---|---|---|
| Bit | 1 bit | 2 |
| Nibble | 4 bits | 16 (one hex digit) |
| Byte | 8 bits | 256 |

Computers also handle data in **words**, the number of bits a processor works with at once, typically 32 or 64 bits.

Each extra bit doubles the number of patterns, so **n bits can represent $$2^n$$ different values**. When those values are the non-negative whole numbers starting at 0, the range is 0 to $$2^n - 1$$. One byte holds 0 to 255; 16 bits hold 0 to 65,535.

The reverse question is just as common: how many bits do you need to give every item its own code? Find the smallest n with $$2^n$$ at least as large as the number of items.

::::example[Bits needed for unique codes]
A school wants a unique binary ID for each of its 1,000 students. What is the minimum number of bits?

:::step
Try powers of two: $$2^9 = 512$$ is too few for 1,000 students.
:::

:::step
$$2^{10} = 1024$$ is enough, with 24 codes to spare.
:::

:::answer
10 bits. In general, the bits needed for N items is the smallest n with $$2^n \ge N$$.
:::
::::

:::trap
**Common trap.** Two more bits do not mean two more values. Going from 8 bits to 10 bits takes you from 256 values to 1,024, four times as many.
:::

::check{id="bits-bytes-01"}

## KB versus KiB: decimal and binary prefixes [Competitive]

Storage sizes use prefixes, and there are two systems that sound almost alike.

| Decimal (SI) prefix | Bytes | Binary (IEC) prefix | Bytes |
|---|---|---|---|
| kilobyte (KB) | 1,000 | kibibyte (KiB) | 1,024 = $$2^{10}$$ |
| megabyte (MB) | 1,000,000 | mebibyte (MiB) | 1,048,576 = $$2^{20}$$ |
| gigabyte (GB) | $$10^9$$ | gibibyte (GiB) | $$2^{30}$$ |
| terabyte (TB) | $$10^{12}$$ | tebibyte (TiB) | $$2^{40}$$ |

Strictly, the decimal prefixes mean powers of 1,000 and the binary ones mean powers of 1,024. In everyday use the line blurs: some software calls 1,024 bytes a "kilobyte". The gap explains a familiar puzzle. A drive sold as 1 TB holds $$10^{12}$$ bytes, and an operating system that counts in binary units reports $$10^{12} / 2^{30} \approx 931$$ "GB".

A second distinction is **bits versus bytes**. Network speeds are quoted in bits per second (Mbps, megabits per second), while file sizes are in bytes (MB). Since a byte is 8 bits, divide a speed in bits by 8 to get bytes: 100 Mbps moves at most 12.5 MB per second. A lowercase b means bits and an uppercase B means bytes.

::::example[Download time]
How long does a 500 MB file take to download at 100 Mbps, at best?

:::step
Convert the file to bits: 500 MB times 8 is 4,000 megabits.
:::

:::step
Divide by the speed: 4,000 megabits divided by 100 megabits per second is 40 seconds.
:::

:::answer
40 seconds. Forgetting the factor of 8 gives 5 seconds, a classic wrong choice.
:::
::::

::check{id="bits-bytes-02"}

## Binary addition and overflow [Competitive]

Binary addition works like decimal addition, carrying whenever a column reaches the base. There are only four facts to know:

| Sum | Result |
|---|---|
| 0 + 0 | 0 |
| 0 + 1 | 1 |
| 1 + 1 | 10 (write 0, carry 1) |
| 1 + 1 + 1 | 11 (write 1, carry 1) |

::::example[Adding binary numbers]
Add $$1011_2$$ and $$0110_2$$.

:::step
Rightmost column: 1 + 0 = 1. Next column: 1 + 1 = 10, so write 0 and carry 1.
:::

:::step
Third column: 0 + 1 + the carried 1 = 10, so write 0 and carry 1. Fourth column: 1 + 0 + the carried 1 = 10, so write 0 and carry 1.
:::

:::step
The final carry becomes a new leftmost digit: 10001.
:::

:::answer
$$1011_2 + 0110_2 = 10001_2$$, which is 11 + 6 = 17.
:::
::::

Computers store numbers in a fixed number of bits. When a result needs more bits than are available, the extra carry is lost. This is **overflow**. An 8-bit unsigned value tops out at 255, so 200 + 100 = 300 does not fit: the stored result is 300 minus 256, which is 44. Overflow is why counters "wrap around" to small values and why choosing a large enough data type matters.

::check{id="bin-arith-01"}

## Two's complement for negative numbers [Champion]

To store negative whole numbers, almost every computer uses **two's complement**. In n bits, the leftmost bit is given a negative weight of $$-2^{n-1}$$, and the others keep their usual positive weights. For 8 bits, the leftmost bit is worth negative 128, so:

- The range is negative 128 to 127. In general it is $$-2^{n-1}$$ to $$2^{n-1} - 1$$.
- A leftmost bit of 0 means the number is zero or positive; a leftmost bit of 1 means it is negative.

To negate a number, **flip every bit, then add 1**.

::::example[Negating in two's complement]
Write negative 5 as an 8-bit two's complement number, then read it back.

:::step
Positive 5 in 8 bits is 00000101.
:::

:::step
Flip every bit: 11111010. Add 1: 11111011.
:::

:::step
Read it back with the leftmost bit worth negative 128: negative 128 + 64 + 32 + 16 + 8 + 2 + 1 = negative 5.
:::

:::answer
Negative 5 is 11111011 in 8-bit two's complement.
:::
::::

Why this design? The same addition circuit works for positive and negative numbers, and there is only one way to write zero. A simpler idea, a separate sign bit, would need special rules for adding and would have both a positive and a negative zero.

:::trap
**Common trap.** Stopping after flipping the bits gives the one's complement (11111010), not the two's complement. Do not forget to add 1.
:::

::check{id="bin-arith-02"}

## Fractions and floating-point rounding [Champion]

Most decimal numbers with fractions, such as prices and measurements, are stored as **floating-point** numbers: a binary version of scientific notation. Just as 1/3 has no exact decimal form (0.333...), many simple decimals such as 0.1 have no exact binary form. The computer stores the nearest value it can, and tiny rounding errors appear:

```python run
import math

print(0.1 + 0.2)
print(0.1 + 0.2 == 0.3)
print(math.isclose(0.1 + 0.2, 0.3))
```

```output
0.30000000000000004
False
True
```

Two practical rules follow. Never test floating-point numbers for exact equality; compare them within a small tolerance instead, as `math.isclose` does. And when exact cents matter, store money as a whole number of cents or use a decimal type. Floating-point formats also have limits at both ends: a result too large to represent overflows, and one too close to zero can **underflow** to zero.

::check{id="bin-arith-06"}

## Text: ASCII, Unicode, and UTF-8

Characters are stored as numbers too. A **character encoding** is the agreement about which number stands for which character.

**ASCII** (American Standard Code for Information Interchange) is a 7-bit code with 128 characters: English letters, digits, punctuation, and control codes such as a new line. A few codes are worth memorizing:

| Character | Space | 0 | A | Z | a | z |
|---|---|---|---|---|---|---|
| Decimal code | 32 | 48 | 65 | 90 | 97 | 122 |
| Hex code | 20 | 30 | 41 | 5A | 61 | 7A |

Letters are in order, so B is 66 and C is 67. Each lowercase letter is exactly **32 more** than its uppercase partner, so if G is 71, g is 103.

ASCII has no room for é, ñ, Chinese characters, or mathematical symbols. **Unicode** fixes that: it is a universal standard that gives every character in virtually every writing system its own number, called a **code point** and written like U+0041 (that is A, hex 41, the same as ASCII).

Unicode says which number each character gets; an encoding says how to store that number in bytes. **UTF-8** is by far the most common encoding on the web. It uses **1 to 4 bytes per character**: the first 128 code points (exactly the ASCII characters) take 1 byte with the same values as ASCII, so plain ASCII text is already valid UTF-8. Accented letters such as é take 2 bytes, many other symbols such as the euro sign take 3, and some rarer characters take 4.

```python run
print(ord("A"), ord("a"), chr(66))
print(len("café"), len("café".encode("utf-8")))
print("é".encode("utf-8"))
```

```output
65 97 B
4 5
b'\xc3\xa9'
```

"café" has 4 characters but 5 bytes in UTF-8, because é is the two bytes C3 A9. If a program reads those bytes with the wrong encoding, each byte turns into a separate wrong character and "café" shows up as "cafÃ©". Garbled text like this almost always means a text file was decoded with a different encoding than it was saved in.

## Colors: hex codes and RGB

Screens build every color from red, green, and blue light. In the common **RGB** scheme, each channel is one byte, a number from 0 to 255, so a color takes 3 bytes (24 bits). That allows $$256^3 = 2^{24} = 16{,}777{,}216$$ different colors.

A **hex color code** writes the three bytes as six hex digits: #RRGGBB, two digits per channel.

::::example[Hex color to RGB]
What RGB values does #FF8000 represent?

:::step
Split into pairs: FF, 80, 00.
:::

:::step
Convert each pair: FF is 15 times 16 + 15 = 255, 80 is 8 times 16 = 128, and 00 is 0.
:::

:::answer
#FF8000 is red 255, green 128, blue 0: full red with half green, which is orange.
:::
::::

Going the other way, RGB (34, 139, 34) becomes 22, 8B, 22 in hex, so #228B22. Reference points help: #000000 is black, #FFFFFF is white, #FF0000 is pure red, and equal channels such as #808080 give gray.

::check{id="media-encoding-01"}

## Images and sound as numbers, and file-size math [Competitive]

An image is a grid of **pixels**, and each pixel is stored as numbers. In a grayscale image, each pixel is one byte from 0 (black) to 255 (white); in a color image, each pixel is three bytes of RGB.

```figure
type: pixels
caption: A 6 by 6 grayscale image is just 36 numbers, each from 0 (black) to 255 (white). The dark pixels here form a simple face.
grid:
  - [255, 255, 255, 255, 255, 255]
  - [255, 30, 255, 255, 30, 255]
  - [255, 255, 255, 255, 255, 255]
  - [30, 255, 255, 255, 255, 30]
  - [255, 30, 30, 30, 30, 255]
  - [255, 255, 255, 255, 255, 255]
```

That makes uncompressed file sizes simple multiplication:

$$
\text{image bytes} = \text{width} \times \text{height} \times \text{bytes per pixel}
$$

A 1920 by 1080 color image takes $$1920 \times 1080 \times 3 = 6{,}220{,}800$$ bytes, about 6.2 MB, before compression.

Sound is recorded by **sampling** the sound wave thousands of times per second. Each sample is a number with a fixed **bit depth**, and stereo sound stores two channels:

$$
\text{audio bits} = \text{sample rate} \times \text{bit depth} \times \text{channels} \times \text{seconds}
$$

CD-quality audio uses 44,100 samples per second at 16 bits in stereo: $$44{,}100 \times 16 \times 2 = 1{,}411{,}200$$ bits per second. One minute is 84,672,000 bits, or about 10.6 MB after dividing by 8.

Real files are usually much smaller because they are compressed. **Lossless** compression (PNG images, FLAC audio, ZIP files) shrinks a file so that the original can be rebuilt exactly. **Lossy** compression (JPEG images, MP3 audio, most video) throws away detail that people barely notice, which makes files far smaller, but the discarded detail is gone for good.

:::tip
**Test tip.** On file-size questions, watch three things: the bytes per pixel or the number of channels, whether the answer is wanted in bits or bytes, and whether a kilobyte means 1,000 or 1,024 bytes.
:::

:::takeaways
- 1 byte = 8 bits; a nibble = 4 bits. n bits hold $$2^n$$ values, 0 to $$2^n - 1$$ unsigned. Bits needed for N items: the smallest n with $$2^n \ge N$$.
- KB = 1,000 bytes and KiB = 1,024 bytes (MB vs MiB, and so on). A "1 TB" drive shows about 931 binary GB.
- Network speeds are in bits; file sizes are in bytes. Divide bits by 8.
- Binary addition carries at 2. Overflow: a fixed number of bits drops the extra carry, so 200 + 100 in 8 bits stores 44.
- Two's complement: flip the bits and add 1. In 8 bits the range is negative 128 to 127, and a leading 1 means negative.
- Floating point cannot store many decimals exactly (0.1 + 0.2 is not exactly 0.3). Compare with a tolerance.
- ASCII: 7 bits, 128 characters; A = 65, a = 97, 0 = 48, space = 32; lowercase is uppercase + 32. Unicode gives every character a code point; UTF-8 stores it in 1 to 4 bytes and matches ASCII for the first 128.
- RGB: 3 bytes per pixel, 16,777,216 colors; #RRGGBB in hex. Image bytes = width x height x bytes per pixel. Audio bits = rate x depth x channels x seconds.
- Lossless compression rebuilds the original exactly (PNG, FLAC, ZIP); lossy discards detail (JPEG, MP3).
:::
