title: "SQL: aggregating and grouping"
---

Analysts rarely want every row; they want totals, averages, and counts, often per group: average GPA by grade, sales by category, orders per customer. This lesson covers the aggregate functions, GROUP BY, and HAVING, and then the idea that unlocks the trickiest SQL questions: the order in which a database actually processes a query, which is not the order in which you write it. Examples use the **school** and **shop** databases.

## Aggregate functions

An **aggregate function** turns many rows into one summary value. The five you need:

| Function | Returns |
|---|---|
| COUNT | The number of rows or values |
| SUM | The total of a numeric column |
| AVG | The mean of a numeric column |
| MIN | The smallest value |
| MAX | The largest value |

```sql run db=school
SELECT COUNT(*) AS students, ROUND(AVG(gpa), 2) AS avg_gpa,
       MIN(gpa) AS lowest, MAX(gpa) AS highest
FROM students;
```

| students | avg_gpa | lowest | highest |
|---|---|---|---|
| 10 | 3.37 | 2.5 | 3.9 |

Without GROUP BY, an aggregate query treats the whole table as one group and returns exactly one row. `ROUND(value, 2)` rounds to two decimal places. As lesson 4.2 showed, every aggregate except `COUNT(*)` skips NULLs, so this AVG divides the sum of the 9 known GPAs by 9, not by 10.

## COUNT(*) versus COUNT(column) [Competitive]

COUNT comes in three forms, and the test likes to put them side by side:

- `COUNT(*)` counts **rows**, whatever they contain.
- `COUNT(column)` counts the **non-NULL values** in that column.
- `COUNT(DISTINCT column)` counts the **different non-NULL values**.

The enrollments table has 13 rows, two scores are NULL, and 9 different students are enrolled:

```sql run db=school
SELECT COUNT(*) AS enrollments, COUNT(score) AS scored,
       COUNT(DISTINCT student_id) AS students
FROM enrollments;
```

| enrollments | scored | students |
|---|---|---|
| 13 | 11 | 9 |

::check{id="sql-aggregate-02"}

## GROUP BY

**GROUP BY** splits the rows into groups that share a value, then computes each aggregate separately for every group. The result has **one row per group**:

```sql run db=school
SELECT grade, COUNT(*) AS students, ROUND(AVG(gpa), 2) AS avg_gpa
FROM students
GROUP BY grade
ORDER BY grade;
```

| grade | students | avg_gpa |
|---|---|---|
| 9 | 1 | 3.4 |
| 10 | 3 | 3.4 |
| 11 | 3 | 3.53 |
| 12 | 3 | 3.17 |

Look closely at grade 10: COUNT(*) is 3, but its average uses only Ava (3.6) and Dev (3.2), because Isla's GPA is NULL. (3.6 + 3.2) / 2 = 3.4.

NULL values form a group of their own. Grouping students by club gives four groups, one of them for the two students with no club:

```sql run db=school
SELECT club_id, COUNT(*) AS members
FROM students
GROUP BY club_id
ORDER BY club_id;
```

| club_id | members |
|---|---|
| NULL | 2 |
| 1 | 3 |
| 2 | 3 |
| 3 | 2 |

(SQLite sorts the NULL group first; PostgreSQL would list it last.)

A grouped query has one firm rule: **every column in SELECT must either appear in GROUP BY or sit inside an aggregate.** The query `SELECT grade, name, COUNT(*) FROM students GROUP BY grade` breaks the rule, because a grade group holds several names and SQL cannot know which one to show. Standard SQL rejects it; a few systems, including SQLite, quietly pick one name, which is worse.

:::tip
**Test tip.** To count the rows a grouped query returns, count the distinct values of the GROUP BY column (after WHERE has filtered), then remove any groups that HAVING throws out.
:::

::check{id="sql-aggregate-03"}

## HAVING versus WHERE

WHERE and HAVING both filter, but at different moments:

- **WHERE** filters **rows**, before any grouping happens.
- **HAVING** filters **groups**, after the aggregates are computed.

Because groups do not exist yet when WHERE runs, an aggregate such as `COUNT(*) > 2` can appear only in HAVING. This query keeps students with GPAs above 3.0, groups them by grade, then keeps only grades with at least two such students:

```sql run db=school
SELECT grade, COUNT(*) AS students
FROM students
WHERE gpa > 3.0
GROUP BY grade
HAVING COUNT(*) >= 2
ORDER BY grade;
```

| grade | students |
|---|---|
| 10 | 2 |
| 11 | 2 |
| 12 | 2 |

Grade 9 disappears: Grace passes the WHERE filter, but Grace's group of one fails the HAVING test.

:::trap
**Common trap.** `WHERE COUNT(*) >= 2` is an error, not a filter. Conditions on aggregates go in HAVING; conditions on individual rows go in WHERE.
:::

::check{id="sql-aggregate-04"}

## The logical processing order [Competitive]

You write a query in one order, but the database processes it in another:

| Written order | Logical processing order |
|---|---|
| 1. SELECT | 1. FROM |
| 2. FROM | 2. WHERE |
| 3. WHERE | 3. GROUP BY |
| 4. GROUP BY | 4. HAVING |
| 5. HAVING | 5. SELECT (then DISTINCT) |
| 6. ORDER BY | 6. ORDER BY |
| 7. LIMIT | 7. LIMIT |

The database first gathers the rows (FROM), filters them (WHERE), forms groups (GROUP BY), filters the groups (HAVING), computes the output columns (SELECT), sorts (ORDER BY), and finally trims (LIMIT).

This order explains several rules at once:

- **An alias does not exist in WHERE.** In `SELECT gpa * 25 AS pct FROM students WHERE pct > 90`, WHERE runs before SELECT has created `pct`, so standard SQL (and PostgreSQL) rejects it. Repeat the expression instead: `WHERE gpa * 25 > 90`. SQLite happens to accept the alias, as a nonstandard extension.
- **ORDER BY can use an alias**, because it runs after SELECT.
- **Aggregates cannot go in WHERE**, because groups are formed after WHERE.
- **LIMIT comes last**, so it trims the final, sorted result.

Try it: step through this query clause by clause and watch the rows shrink, group, and sort in the logical order.

## Top-N queries

Combining GROUP BY, ORDER BY, and LIMIT answers "which are the top few?" questions. Which two products sold the most units in the shop database?

```sql run db=shop
SELECT product_id, SUM(quantity) AS units
FROM order_items
GROUP BY product_id
ORDER BY units DESC, product_id
LIMIT 2;
```

| product_id | units |
|---|---|
| 102 | 7 |
| 101 | 6 |

The recipe: group by the item, aggregate the measure, sort by that aggregate descending, and limit. Add a second sort column so ties come out in a predictable order. If ties at the cutoff should all be kept, SQL Server offers `TOP n WITH TIES`, which can return more than n rows.

::check{id="sql-aggregate-05"}

:::takeaways
- Aggregate functions summarize rows: COUNT, SUM, AVG, MIN, MAX. Without GROUP BY, an aggregate query returns one row.
- COUNT(*) counts rows; COUNT(column) counts non-NULL values; COUNT(DISTINCT column) counts different non-NULL values. AVG and the others skip NULLs.
- GROUP BY returns one row per group, and NULL forms its own group. Every SELECT column must be grouped or aggregated.
- WHERE filters rows before grouping; HAVING filters groups after aggregation. Aggregates belong in HAVING, never in WHERE.
- Written order: SELECT, FROM, WHERE, GROUP BY, HAVING, ORDER BY, LIMIT. Logical order: FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT.
- A SELECT alias cannot be used in WHERE (standard SQL) but can be used in ORDER BY.
- Top-N: group, aggregate, ORDER BY the aggregate DESC, then LIMIT.
:::
