title: Training, validation, and test data
---

A model is only useful if it works on data it has never seen, and the only honest way to find out is to hold some data back. One objective asks you to describe the use of training, test, and validation datasets, and questions test exactly what each split is for, how big each one usually is, how cross-validation works, and how information can leak between splits and make a model look better than it is. Every idea here comes back to one principle: never judge a model on data it learned from.

## What each split is for

Before training, the data is divided into three parts:

- The **training dataset** is the data the model learns from. Training fits the model's parameters, such as its weights or coefficients, to these examples.
- The **validation dataset** is held out from training and used during development: to compare different models, to tune hyperparameters such as tree depth or learning rate, and to decide when to stop training.
- The **test dataset** is held out until the very end and used once, to estimate how well the final model will perform on new data.

A school analogy helps. The training set is the homework, where learning happens. The validation set is the practice quizzes, used to adjust how you study. The test set is the final exam, which measures what you actually learned, and it only means something if you have not seen its questions before.

:::key
**Key idea.** Training data fits the parameters, validation data tunes the choices, and test data gives the final, honest score.
:::

::check{id="data-splits-01"}

## Typical split sizes and stratification

Common splits are about 70% training, 15% validation, and 15% test, or 80%, 10%, and 10%. When only a training and a test set are used, 80% and 20% is typical. Very large datasets can hold out smaller percentages: with 10 million examples, even 1% is 100,000 examples, which is plenty to measure performance, so more of the data can go to training.

The rows are usually **shuffled** and assigned at random, so that each split resembles the whole dataset. For classification with **imbalanced classes**, random assignment can go wrong: if only 2% of transactions are fraud, a small random test set might contain almost no fraud at all. A **stratified split** fixes this by keeping the class proportions the same in every split.

::::example[Sizing a stratified split]
A dataset has 10,000 examples, 2% of them positive (fraud). It is split 70/15/15 with stratification. How many examples, and how many positives, go to each split?

:::step
Sizes: 70% of 10,000 is 7,000 for training; 15% is 1,500 each for validation and test.
:::

:::step
Positives: 2% of 10,000 is 200 in all. Stratification keeps 2% in each split: 0.02 × 7,000 = 140 for training, and 0.02 × 1,500 = 30 each for validation and test.
:::

:::answer
Training gets 7,000 examples (140 positive); validation and test get 1,500 each (30 positive each).
:::
::::

## Why the test set is used once

It is tempting to check the test set, adjust the model, and check again. Doing that turns the test set into a second validation set: every adjustment that improves the test score fits the model a little more closely to those particular examples. The final test score then overstates how well the model will do on genuinely new data, because the model has, indirectly, been tuned to the test.

So the test set stays locked away while models are compared and tuned, and it is used once, at the end, to report performance. Repeated decisions are the validation set's job. The same logic is why early stopping, which halts training when validation error stops improving, watches the validation set and never the test set.

:::trap
**Common trap.** The validation set and the test set are not interchangeable. The validation set guides choices during development; the test set is touched only after every choice has been made.
:::

::check{id="data-splits-03"}

## k-fold cross-validation [Competitive]

A single validation set can be unlucky, and with a small dataset, setting aside 15% or 20% of the data hurts. **Cross-validation** solves both problems. In **k-fold cross-validation**, the data is divided into k equal parts called **folds**. The model is trained k times, each time using one fold for validation and the other k - 1 folds for training, and the k validation scores are averaged.

With 5 folds, each round holds out a different fold:

| Round | Fold 1 | Fold 2 | Fold 3 | Fold 4 | Fold 5 |
|---|---|---|---|---|---|
| 1 | Validate | Train | Train | Train | Train |
| 2 | Train | Validate | Train | Train | Train |
| 3 | Train | Train | Validate | Train | Train |
| 4 | Train | Train | Train | Validate | Train |
| 5 | Train | Train | Train | Train | Validate |

With 1,000 examples and k = 5, each fold has 200 examples, so each of the 5 models trains on 800 and is validated on 200. Every example is used for validation exactly once and for training k - 1 times.

Cross-validation gives a more reliable estimate than a single split, especially for small datasets, and the spread of the k scores shows how much performance varies. Its cost is training k models instead of one, which can be too expensive for very large models. **Leave-one-out cross-validation** (LOOCV) is the extreme case, k = n: with 50 examples, it trains 50 models, each leaving out one example. For classification, **stratified k-fold** keeps the class proportions the same in every fold. A final test set is still held back for the end.

::check{id="cross-validation-01"}

## Data leakage [Competitive]

**Data leakage** happens when information that would not be available at prediction time, or information from the validation or test data, slips into training. The model then looks excellent in testing and fails in real use. Three forms are common:

- **Target leakage**: a feature that is really a consequence of the target. A model that predicts pneumonia using the feature "received antibiotics for pneumonia" will score superbly, because the treatment happens after the diagnosis; at prediction time, that information does not exist yet.
- **Preprocessing leakage**: fitting a scaler, an imputer, or a feature-selection step on all the data before splitting it, so statistics from the test rows shape the training (lesson 4.7). The fix is to split first and fit every preprocessing step on the training data only.
- **Overlap between splits**: the same customer or patient appearing in both training and test data, often through repeated rows. The model recognizes the individual instead of learning a pattern. The fix is to split by individual, keeping all of a person's rows in one split.

The symptoms are recognizable: a score that seems too good to be true, a single feature that dominates the model, and performance that collapses once the model is deployed.

::check{id="leakage-01"}

## Splitting time series [Champion]

When data is ordered in time, such as daily sales or stock prices, a random split leaks the future into the past. If the training set contains next Tuesday and the test set contains this Monday, the model learns from information it could never have had when making a real forecast.

Time series are split **chronologically**: train on the earlier period and test on a later one. Cross-validation is done with rolling or expanding windows: train on months 1 to 6 and test on month 7, then train on months 1 to 7 and test on month 8, and so on. Features must also respect time: a feature for a given day may use only information available by that day, not, for example, an average computed over the whole month including days that had not happened yet.

::check{id="leakage-02"}

:::takeaways
- The training set fits the parameters; the validation set tunes hyperparameters, compares models, and drives early stopping; the test set gives one final, unbiased estimate.
- Typical splits: 70/15/15, 80/10/10, or 80/20 with no validation set. Huge datasets can hold out smaller percentages.
- Shuffle before random splits. Stratified splits keep class proportions equal across splits, which matters for imbalanced classes.
- Reusing the test set to make decisions makes its score optimistic. Use it once, at the end.
- k-fold cross-validation trains k models, each validated on a different fold and trained on the other k - 1; average the scores. LOOCV uses k = n.
- Data leakage: target leakage (features that come from the outcome), preprocessing before splitting, and overlap between splits. Symptoms: scores too good to be true that collapse in deployment.
- Split time series chronologically, and build features only from information available at the time.
:::
