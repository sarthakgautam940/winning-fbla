Real questions span tables: which club is each student in, which customers have never ordered, which course has the highest average score. This lesson covers joins and the row counts they produce, subqueries, set operations, the statements that change data and tables, and, for the champion tier, window functions and common table expressions. Join questions are among the most common SQL items on tests like this one, and the row-count questions are where careful students gain points.

## INNER JOIN

A **JOIN** combines rows from two tables by matching values in related columns, usually a foreign key in one table and the primary key it points to. The `ON` clause states the match. Short **table aliases** such as `s` and `c` keep the query readable:

```sql run db=school
SELECT s.name, c.club_name
FROM students s
INNER JOIN clubs c ON s.club_id = c.club_id
ORDER BY s.name;
```

| name | club_name |
|---|---|
| Ava | Robotics |
| Chloe | Debate |
| Dev | Robotics |
| Elena | Data Science |
| Grace | Debate |
| Hiro | Robotics |
| Isla | Data Science |
| Jonah | Debate |

An **INNER JOIN** keeps only the pairs of rows that match. Ben and Farid have no club (their `club_id` is NULL), and NULL never equals anything, so they drop out: 10 students give 8 rows. Chess has no members, so it does not appear either. Writing plain `JOIN` means INNER JOIN.

## LEFT, RIGHT, and FULL OUTER JOIN

**Outer joins** keep rows that have no match, filling the missing side with NULL.

A **LEFT JOIN** keeps every row of the left (first) table. Here are the grade 11 and 12 students with their clubs:

```sql run db=school
SELECT s.name, c.club_name
FROM students s
LEFT JOIN clubs c ON s.club_id = c.club_id
WHERE s.grade >= 11
ORDER BY s.name;
```

| name | club_name |
|---|---|
| Ben | NULL |
| Chloe | Debate |
| Elena | Data Science |
| Farid | NULL |
| Hiro | Robotics |
| Jonah | Debate |

Ben and Farid stay in the result, with NULL in the club column. Across all 10 students, this LEFT JOIN returns 10 rows.

A **RIGHT JOIN** keeps every row of the right (second) table instead; `clubs c RIGHT JOIN students s` gives the same rows as `students s LEFT JOIN clubs c`. A **FULL OUTER JOIN** keeps every row from both tables, matched where possible: all 10 students plus Chess with a NULL name, 11 rows in all.

A LEFT JOIN also finds what is **missing**. To list clubs with no members, keep every club and then keep only those whose student columns came back NULL:

```sql run db=school
SELECT c.club_name
FROM clubs c
LEFT JOIN students s ON s.club_id = c.club_id
WHERE s.student_id IS NULL;
```

| club_name |
|---|
| Chess |

Try it: switch between INNER, LEFT, RIGHT, and FULL joins for the first six students and watch which rows survive and where NULLs appear.

## Counting the rows a join returns [Competitive]

Row-count questions become simple once you sort the rows into three groups: matched pairs, unmatched rows from the left table, and unmatched rows from the right table.

| Join | Rows returned |
|---|---|
| INNER | matched pairs |
| LEFT | matched pairs + unmatched left rows |
| RIGHT | matched pairs + unmatched right rows |
| FULL OUTER | matched pairs + unmatched left + unmatched right |
| CROSS | every combination: rows in left × rows in right |

::::example[Every join of students and clubs]
Students has 10 rows and clubs has 4. Eight students match a club, Ben and Farid match none, and Chess matches no student. Count the rows for each join.

:::step
Matched pairs: 8. Unmatched students: 2. Unmatched clubs: 1.
:::

:::step
INNER = 8. LEFT (students first) = 8 + 2 = 10. RIGHT (clubs second) = 8 + 1 = 9.
:::

:::step
FULL OUTER = 8 + 2 + 1 = 11. CROSS JOIN = 10 × 4 = 40, every student paired with every club.
:::

:::answer
8, 10, 9, 11, and 40.
:::
::::

**Duplicate keys multiply rows.** When one row matches several rows on the other side, it appears once per match. Joining students to enrollments gives 13 rows, one per enrollment, because Ava, Chloe, Elena, and Hiro each take two courses. A LEFT JOIN from students to enrollments gives 14 rows: the 13 enrollments plus Isla, who takes no course.

:::trap
**Common trap.** A LEFT JOIN can return more rows than its left table. "Every left row is kept" means no left row disappears, not that each one appears only once.
:::

## Subqueries and EXISTS [Competitive]

A **subquery** is a query nested inside another, written in parentheses. A common use compares each row to a summary of the whole table, such as students above the average GPA:

```sql run db=school
SELECT name, gpa FROM students
WHERE gpa > (SELECT AVG(gpa) FROM students)
ORDER BY gpa DESC, name;
```

| name | gpa |
|---|---|
| Chloe | 3.9 |
| Hiro | 3.9 |
| Elena | 3.8 |
| Ava | 3.6 |
| Grace | 3.4 |

The inner query returns one value, about 3.37, and the outer query compares every GPA to it. A subquery that returns a list works with IN: `WHERE club_id IN (SELECT club_id FROM clubs WHERE advisor = 'Ms. Park')` finds Ms. Park's club members, Ava, Dev, and Hiro.

**EXISTS** is true when its subquery returns at least one row. This subquery is **correlated**: it refers to the outer query's current club, so it runs once for each club:

```sql run db=school
SELECT club_name FROM clubs c
WHERE EXISTS (SELECT 1 FROM students s WHERE s.club_id = c.club_id)
ORDER BY club_name;
```

| club_name |
|---|
| Data Science |
| Debate |
| Robotics |

:::trap
**Common trap.** `NOT IN` breaks when its list contains a NULL. `SELECT club_name FROM clubs WHERE club_id NOT IN (SELECT club_id FROM students)` returns **no rows at all**, not Chess, because the list includes the NULLs of Ben and Farid, and "not equal to an unknown value" is never true. Filter out the NULLs in the subquery, or use NOT EXISTS or the LEFT JOIN pattern above.
:::

::check{id="sql-subqueries-01"}

## UNION, INTERSECT, EXCEPT [Competitive]

**Set operations** combine the results of two queries that return the same number of columns with compatible types. In the school database, the students taking STAT1 are 1, 2, 4, 5, and 8, and the students taking CS1 are 1, 3, 6, and 8:

| Operation | Keeps | Result for STAT1 versus CS1 |
|---|---|---|
| UNION | Rows in either result, duplicates removed | 1, 2, 3, 4, 5, 6, 8 (7 rows) |
| UNION ALL | Rows in either result, duplicates kept | 9 rows, with 1 and 8 twice |
| INTERSECT | Rows in both results | 1, 8 |
| EXCEPT | Rows in the first result but not the second | 2, 4, 5 |

```sql run db=school
SELECT student_id FROM enrollments WHERE course_id = 'STAT1'
INTERSECT
SELECT student_id FROM enrollments WHERE course_id = 'CS1';
```

| student_id |
|---|
| 1 |
| 8 |

UNION removes duplicates, which takes extra work; use UNION ALL when duplicates are fine or impossible. Oracle calls EXCEPT by the name MINUS.

::check{id="sql-subqueries-02"}

## INSERT, UPDATE, DELETE, CREATE TABLE

SQL statements fall into four families:

- **DDL** (data definition language) defines structure: CREATE, ALTER, DROP, TRUNCATE.
- **DML** (data manipulation language) works with rows: SELECT, INSERT, UPDATE, DELETE. (Some sources put SELECT in its own family, DQL, for data query language.)
- **DCL** (data control language) manages permissions: GRANT, REVOKE.
- **TCL** (transaction control language) manages transactions: COMMIT, ROLLBACK.

The core DML statements:

```sql
INSERT INTO clubs (club_id, club_name, advisor)
VALUES (5, 'Film', 'Mr. Diaz');

UPDATE students
SET club_id = 4
WHERE student_id = 2;

DELETE FROM enrollments
WHERE score IS NULL;
```

**UPDATE** and **DELETE** act on every row their WHERE clause matches, and **without a WHERE clause they act on every row in the table**. `DELETE FROM enrollments;` empties the table (the table itself remains), and `UPDATE students SET club_id = 4;` puts every student in Chess. Inside a transaction, ROLLBACK can undo such a mistake.

**CREATE TABLE** defines a table with its columns, types, and constraints (lesson 4.1):

```sql
CREATE TABLE attendance (
  student_id  INTEGER NOT NULL REFERENCES students(student_id),
  attended_on TEXT NOT NULL,
  present     INTEGER NOT NULL CHECK (present IN (0, 1)),
  PRIMARY KEY (student_id, attended_on)
);
```

Three ways to remove data are easy to confuse:

| Statement | What it removes |
|---|---|
| DELETE FROM t WHERE ... | The rows that match (all rows if there is no WHERE); the table remains |
| TRUNCATE TABLE t | Every row, quickly, with no WHERE allowed; the table remains |
| DROP TABLE t | The whole table: its rows, its columns, and its definition |

Whether TRUNCATE can be rolled back differs between database systems, so treat it as permanent unless you know your system.

## Window functions and CTEs [Champion]

A **window function** computes a value for each row from a set of related rows, its **window**, without collapsing the rows the way GROUP BY does. It is written with `OVER`:

```sql run db=school
SELECT name, gpa,
       ROW_NUMBER() OVER (ORDER BY gpa DESC, name) AS row_num,
       RANK()       OVER (ORDER BY gpa DESC) AS rnk,
       DENSE_RANK() OVER (ORDER BY gpa DESC) AS dense
FROM students
WHERE gpa >= 3.6
ORDER BY gpa DESC, name;
```

| name | gpa | row_num | rnk | dense |
|---|---|---|---|---|
| Chloe | 3.9 | 1 | 1 | 1 |
| Hiro | 3.9 | 2 | 1 | 1 |
| Elena | 3.8 | 3 | 3 | 2 |
| Ava | 3.6 | 4 | 4 | 3 |

The three ranking functions differ only at ties:

- **ROW_NUMBER** numbers rows 1, 2, 3, 4 with no ties.
- **RANK** gives tied rows the same rank and then skips ahead: 1, 1, 3, 4.
- **DENSE_RANK** gives tied rows the same rank without gaps: 1, 1, 2, 3.

**PARTITION BY** restarts the window for each group, so this ranks students within their own grade:

```sql run db=school
SELECT name, grade, gpa,
       RANK() OVER (PARTITION BY grade ORDER BY gpa DESC) AS rank_in_grade
FROM students
WHERE grade IN (11, 12)
ORDER BY grade, rank_in_grade;
```

| name | grade | gpa | rank_in_grade |
|---|---|---|---|
| Hiro | 11 | 3.9 | 1 |
| Elena | 11 | 3.8 | 2 |
| Ben | 11 | 2.9 | 3 |
| Chloe | 12 | 3.9 | 1 |
| Jonah | 12 | 3.1 | 2 |
| Farid | 12 | 2.5 | 3 |

A **common table expression** (CTE), written with `WITH`, gives a subquery a name so the main query can use it like a table. CTEs make long queries readable. This one totals the units in each order, then adds a **running total** with a window function:

```sql run db=shop
WITH units AS (
  SELECT order_id, SUM(quantity) AS units
  FROM order_items
  GROUP BY order_id
)
SELECT order_id, units,
       SUM(units) OVER (ORDER BY order_id) AS running_units
FROM units
ORDER BY order_id;
```

| order_id | units | running_units |
|---|---|---|
| 1001 | 5 | 5 |
| 1002 | 1 | 6 |
| 1003 | 3 | 9 |
| 1004 | 5 | 14 |
| 1005 | 1 | 15 |
| 1006 | 3 | 18 |

::check{id="sql-window-01"}

:::takeaways
- JOIN combines tables by matching columns in an ON clause. INNER JOIN keeps only matches; NULL keys never match.
- LEFT JOIN keeps every left row (NULLs fill the right side); RIGHT JOIN keeps every right row; FULL OUTER JOIN keeps all rows from both. LEFT JOIN with WHERE right.key IS NULL finds unmatched rows.
- Row counts: INNER = matches; LEFT = matches + unmatched left; FULL = matches + both unmatched sets; CROSS = left rows × right rows. Duplicate keys multiply rows.
- A subquery nests a query in parentheses: compare to an aggregate, test with IN, or test with EXISTS. NOT IN returns nothing if its list contains NULL.
- UNION removes duplicates, UNION ALL keeps them; INTERSECT keeps rows in both; EXCEPT (Oracle's MINUS) keeps rows only in the first.
- DDL defines structure (CREATE, ALTER, DROP, TRUNCATE); DML handles rows (SELECT, INSERT, UPDATE, DELETE); DCL grants permissions; TCL controls transactions. UPDATE or DELETE without WHERE changes every row.
- DELETE removes chosen rows, TRUNCATE removes all rows, DROP removes the table itself.
- Window functions compute per row without collapsing rows. ROW_NUMBER: 1, 2, 3, 4; RANK: 1, 1, 3, 4; DENSE_RANK: 1, 1, 2, 3. PARTITION BY restarts per group; WITH defines a named CTE.
:::
